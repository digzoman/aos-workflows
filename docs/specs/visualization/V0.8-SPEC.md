# AOS-W 0.8.0 Workflow Visualization Specification

**Status:** New minor preview feature, specification plus reference viewer and optional generator. October 22, 2026. This is additive and does not constitute stable Version 1 acceptance or approval of the original draft PRD.

## User objective

Every AOS-W-capable agent should be able to create an interactive browser page showing the structure of a workflow, its progress, dependencies and details. The diagram shows cards and directional arrows with multiple branches and joins. Clicking any card opens a detail panel with its exact prompt/instructions, input/output contracts, QA criteria, reviewer and approval records, retries, ownership, artifacts and current blockers. The visualization is read-only.

The feature must work even when the environment has no web server, Git, Python, MCP service, database, scheduler or external Internet. A standard offline HTML/JS/CSS/SVG page can be generated by an agent that knows how to read and write the source files. A developer helper is optional.

## Modes

- TEMPLATE. Reads a master or custom template.yaml. Renders all steps and dependencies; statuses are NOT_STARTED, never invented as completed.
- INSTANCE. Reads immutable agent-files/instances/<id>/graph-revisions/gXXXX.yaml and pinned effective configuration. Gives the customized diagram. No fabricated run progress.
- RUN. Uses the exact selected pinned graph and run state, checkpoints, event ledger, reviews, attempts and artifacts. Status comes from on-disk records and must be labeled UNVERIFIED if no independent event reconciliation was performed. Provider truth is never inferred.

Rendering a visualization is not creating a workflow, moving a task, accepting a review, granting an approval, or contacting an external account.

## Required diagram behavior

1. Build a directed graph from stable graph.nodes[].id and graph.nodes[].needs, preserving fan-out, fan-in, conditional branches and join nodes. Visually distinguish node kinds task, review, approval, join and child_generator.
2. Automatically lay out columns from graph predecessor depth, with clear directional SVG arrows, horizontal scroll for complex workflows and responsive detail layout on narrower screens.
3. Show a readable label, stable ID and explicit status text on every node. Use statuses in addition to color, never color alone.
4. Open a detail panel on click or keyboard activation. Preserve the complete stored instructions, not a rewritten AI paraphrase. Display IDs, dependencies, all configured step inputs/outputs, done_when, quality gates, conditional when, retries, assigned actor, attempts, accepted/rejected exact-artifact reviews and evidence references when present.
5. Offer text search, summary counters, complete count and progress bar. A stale or uncertain state must be labeled as such. No automatic background refresh is implied.
6. Under future enhancements support collapsed subworkflows, nested child navigation, event timeline, zoom/pan, graph diff, verified progress and linked artifacts. These are roadmap items, not v0.8 MVP proof.

## Status and arrow semantics

- Green, COMPLETE or ACCEPTED, **only when actual saved evidence says so**.
- Blue, RUNNING.
- Amber, READY or pending prerequisites.
- Purple, REVIEW_WAIT or WAIT_APPROVAL.
- Red, BLOCKED, NEEDS_REWORK or RECONCILE_REQUIRED.
- Grey, NOT_STARTED, WAIT_DEPENDENCY, UNKNOWN, SKIPPED, CANCELLED, STALE or SUPERSEDED.

Arrows represent dependency/eligibility only. They are NOT proof of actual delivery, Meta publishing, external side effects or review authority. A parent node that references separately generated child runs must not be marked accepted without checking required child reviews and current artifact hashes; a diagram is not a replacement for this enforcement.

## Output and file boundaries

~~~text
aos-w/
  references/                          protected framework
    VISUALIZATION.md
    visualization-viewer.html
  spec/schemas/
    visualization-snapshot.schema.json
  agent-files/                          only normal writable subtree
    visualizations/
      README.md                         clean release seed
      <view-id>/
        index.html                      complete self-contained page
        snapshot.json                   optional source-derived projection
~~~

An agent first writes the page to the local/persistent workspace and can display it if its host supports rendering local HTML. View generation and output files must stay under agent-files/visualizations, never change the protected master template or active run state. If local hosting is unsupported, provide the file through the host. If it cannot be viewed there, recommend GitHub Pages **only after owner opt-in**.

### GitHub Pages fallback

An authorized export would use a separately reviewed sanitized view, for example docs/visualizations/<view-id>/index.html in a deliberately selected Pages repository. Publishing to the public Internet is a consequential action. Do not push raw agent-files, sensitive marketing strategy, customer/CRM records, tokens, private prompts, personally identifiable data or unapproved commercial claims. A Pages copy has no default authentication; enterprise private Pages is a provider-specific option only when separately verified. Do not silently configure Pages or publish an artifact.

## Source data precedence and refresh

For TEMPLATE, use the actual intended master/custom template. For INSTANCE/RUN, use the pinned current graph revision selected in the instance; a new master HEAD cannot replace a running graph. For RUN, read run.json, events.jsonl, checkpoints, state.json and exact current reviews and approval records. The event ledger is history authority; state.json is a derived snapshot. Missing/unverified source means UNKNOWN or SOURCE_SNAPSHOT_UNVERIFIED, never invented PASS.

The view must carry mode, generated_at, graph_revision, run_id, event_seq_observed, verification tier and source provenance. It is a point-in-time snapshot. An agent can regenerate it on request, at checkpoint, at a task transition or at handoff. Automatic live updating is optional later work with a real host watcher/scheduler.

## Visualization snapshot v1.0 data contract

Root required fields: visualization_schema "1.0.0", mode TEMPLATE|INSTANCE|RUN, title, generated_at ISO-8601, verification level and nodes[]. Optional root fields include template_id, run_id, graph_revision, event_seq_observed, source hashes, public_export default false and warning.

A node requires id, needs (array of existing IDs), status and label. Other supported fields include kind, prompt, inputs, outputs, quality, contract, retry, when, owner, attempts, review, evidence, source, child_template and notes. Prompt comes directly from the pinned graph instructions. It can contain plain text and special characters but must not be interpreted as HTML or JS. Missing fields are omitted from the details panel, not generated by a hallucinated inference.

Reject duplicate/invalid identifiers, unknown dependencies, cyclic graphs or unbounded graph sizes. The public viewer should not evaluate workflow code, accept arbitrary styles/scripts from prompts or introduce execution controls.

The complete JSON Schema is shipped under spec/schemas/visualization-snapshot.schema.json. The viewer has a single reserved JSON placeholder. The agent embeds serialized JSON escaping less-than/greater-than/ampersand and JS line separators before replacing the placeholder, then writes a standalone index.html. All dynamic data are rendered by textContent. No CDN, external fonts, cookies, storage, fetch, analytics, provider calls or external account access.

## Rendering choice

Use native offline HTML+CSS+SVG+JavaScript as the default. Mermaid is a possible optional authoring alternative, but its default strict security setting disables node click callbacks; loosening that setting broadens trust. The native viewer keeps interactivity without relaxing Mermaid's security configuration. Relevant reference: https://mermaid.js.org/config/schema-docs/config-properties-securitylevel.html

## Agent generation protocol

1. Identify the requested template, instance or run; if the active context identifies it, do not ask again.
2. Read the right pinned graph, compare state with the verified ledger/checkpoint if available and record uncertainty.
3. Convert nodes with exact instructions/outputs/QA into a minimal schema-compliant snapshot. Never invent prompts or provider statuses.
4. Copy the protected visualization-viewer.html and safely embed the snapshot as nonexecuting JSON.
5. Write only under agent-files/visualizations/<view-id>; include snapshot.json for reproducible regeneration when feasible.
6. Preview/open it in the environment if possible; verify actual arrows, branch joins, displayed status, keyboard/click and one complete prompt.
7. Provide the saved page link/path. On subsequent progress regenerate a fresh timestamped or explicitly replaced view while preserving workflow history.
8. If no render/preview is possible, offer a file download. Suggest a sanitized GitHub Pages export only when needed and never deploy without an explicit new approval.

The optional development helper scripts/aosw-visualize.py reads YAML with PyYAML if available or accepts a prepared JSON snapshot. It is not part of the no-runtime install requirement; agents can construct the page from bundled files alone.

## V0.8 acceptance checklist

- V08-01. Build one offline template view from research-starter with saved full prompts and correct dependency arrows.
- V08-02. Build a compound marketing template diagram showing fan-out, join and more than 10 nodes.
- V08-03. Overlay a real saved run state without converting a derived advisory status into false verified provider truth.
- V08-04. Click/keyboard select displays the exact stored step prompt, requirements, quality gates, attempts, comments and evidence metadata.
- V08-05. Untrusted characters and script-like prompt content remain inert text; no outbound scripts, calls or fetch requests.
- V08-06. Reject unsafe IDs, unknown dependencies, cycles and output symlink/path escapes.
- V08-07. Package the protected viewer, schema, guide and a clean visualizations seed into the v0.8 archive; verify user generated HTML and snapshots survive upgrades.
- V08-08. Confirm local browser render in desktop/mobile view using a real browser. Pure tests cannot claim to have visually verified browser usability.
- V08-09. Generated pages carry source, graph revision, event sequence, snapshot time, scope and honesty warnings; no automatic live claim.
- V08-10. Public GitHub Pages remains explicitly opt-in with separate sanitization and no automatic publication.
