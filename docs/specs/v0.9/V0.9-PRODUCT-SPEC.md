# AOS-W v0.9.0 — Human-First Workflows and Interoperability

**Status:** v0.9.2 portable preview released with accessibility regression coverage; remaining third-party acceptance items are still outstanding. This document remains the full target specification. Stable Version 1 PRD approval is separate. See [IMPLEMENTATION-STATUS.md](IMPLEMENTATION-STATUS.md).
**Created:** 2026-10-22. **Current shipped preview:** 0.9.2. **Original version proposal:** 0.9.0, implemented in preview releases, not stable Version 1.
**Scope:** Standards-facing portable workflow contracts, understandable visual diagrams, instructions that survive agent changes, and browser-first hosted presentation. Related detail: [Visualization and Third-Party Handoff](VISUALIZATION-AND-HANDOFF.md), [Acceptance Matrix](ACCEPTANCE-MATRIX.md).
**User evidence:** Feedback on the private Bucket 9 six-audience g0004 event-89 diagram, October 22, 2026, specifically opaque task IDs, missing standalone source/tool instructions (including "Ads Gallery"), and GitHub code-preview links instead of an actual rendered webpage.
**Unchanged invariants:** File-first/manual minimum; normal writes in agent-files only; Git/Python/MCP/server optional; current template graph and stable IDs remain authoritative; historical artifacts and checkpoints immutable; provider readback external; independent QC and consequential human approvals must not be bypassed; original stable V1 acceptance T01–T04 still open.

## Product decision

AOS-W is a **portable workflow coordination layer** rather than a mandatory agent runtime, marketplace, or GitHub Pages publishing service. v0.9 first makes workflows comprehensible to **humans and independent agents** and improves how the user sees them. Interoperability at boundaries follows public standards; the existing YAML/JSON/JSONL source remains the canonical model.

The release SHALL ship the P0 requirements below, with fixtures and conformance tests. P1 items are opt-in experimental exports/adapters **not release-blocking** unless specifically promoted by the owner. Writing this document does not authorize a code release or public publication.

## P0-01. Human-readable task names are first-class

Every workflow and graph step MUST have separate:
- \`id\`: stable machine identity used for DAG references, checkpoints and migrations; never rewritten just for display.
- \`title\` (human display): a concise, action-oriented phrase, generally 3–8 understandable words, without raw slug/dashes, internal task codes, unexplained abbreviations or false completion claims.
- \`summary\`: one sentence explaining what happens, who benefits, and the expected result.
- \`phase_id\` and \`phase_title\`: meaningful process grouping, not "Stage 1", "Stage 2" unless a stage really has no semantic identity.
- \`lane_id\` and \`lane_title\` where a workflow has parallel workstreams; user can collapse an entire lane (e.g., "HVAC business owners").
- \`kind\` task, review, approval, join or generator and a status that faithfully reflects source data.
- \`description\`, \`short_status_reason\`, and \`next_action\` where known.

The renderer MUST use \`title\` as card heading, \`summary\` in the selected overview and \`phase_title\`/ \`lane_title\` as labels. If older graphs lack titles, a deterministic compatibility mapper may propose a clearly marked *generated display label*; an author or reviewer must approve the human-facing label before publishing a reusable template. Do not translate unknown business jargon by hallucinating meaning. Never change IDs or event references just to improve presentation.

Example Bucket 9 source-to-view:

| Stable internal ID | Card text | Phase | Lane |
| --- | --- | --- | --- |
| \`hvac-installation-owners--research\` | Research HVAC business owners | Research competitors | HVAC businesses |
| \`hvac-installation-owners--qc-research\` | Review HVAC research | Check the research | HVAC businesses |
| \`hvac-installation-owners--image-customize\` | Adapt HVAC ad creative | Create ad materials | HVAC businesses |
| \`human-creative-review\` | Approve creative package | Owner approvals | All six audiences |
| \`launch-batch\` | Launch approved ads together | Campaign launch | Shared campaign |

Raw ID, exact source prompt, artifact paths, schema metadata and JSON policy belong under *Advanced / Technical details*, not in the first screen.

## P0-02. A step must be independently runnable and unambiguous

For every executable step, a **Step Brief** MUST specify:
1. **Purpose:** short, jargon-free description of the action and why.
2. **Current scope:** audience/project/market and explicitly excluded actions.
3. **Where to start:** concrete source URLs or repo-relative paths, the exact workspace root, target run/graph revision and authoritative state location.
4. **Tools:** explicit human-readable tool/product names, official URL or local resource locator, tool purpose, authentication/access prerequisites and safe alternative if unavailable. **Do not assume implicit knowledge of "Ads Gallery".**
5. **Inputs and evidence:** direct file references/identifiers, expected revisions and how to check freshness and source authority.
6. **Procedure:** ordered, reproducible instructions in plain language that do not rely on chat memory ("as discussed", "previously approved", "you know the drill" are forbidden unless backed by a precise artifact or authorization record).
7. **Output:** expected path, format and content.
8. **Completion test:** verifiable \`done_when\`, quality rubric, explicit reviewer identity/independence requirements, error/unknown conditions and retry bounds.
9. **Permissions:** actions allowed, forbidden, and which exact human/provider grants are required before subsequent operations.
10. **Handoff:** next dependent step(s), unresolved questions, what a new agent should read, and persisted evidence/provenance.

Each brief MUST be portable across ChatGPT, Codex, Claude, another hosted agent and an unfamiliar human with authorized access; host-specific interfaces MAY be provided as alternative *adapters*, never the only route.

**Advertising example:** A research brief MUST explicitly name an ad research surface such as **Meta Ad Library** (\`https://www.facebook.com/ads/library/\`) and state whether "Ads Gallery" means this site, a separately configured internal gallery, or another verified provider. These names MUST NOT be silently equated. For each source declare access, countries, categories, keywords, expected captured evidence, as-of timestamp and limitations (visible ad does not establish spend, profit, targeting or conversion). When an internal **Ads Gallery** is essential, the actual canonical URL/location, account access, search/export procedure and fallback MUST be present or the step is BLOCKED_MISSING_RESOURCE. Never invent the URL or claim an unseen gallery was accessed.

The **Step Brief** is a human-oriented authoritative derived projection of graph instructions + pinned referenced files. It cannot silently replace or contradict \`graph.nodes[].instructions\`; conflicting instructions must be resolved in a new approved graph revision, preserving old revisions and state. Before adding new required Step Brief fields to an existing template, offer an advisory generated view (not a schema-breaking hard reject) and migrate deliberately.

## P0-03. A visualization is a human navigation interface, not a raw schema dump

- Default view has an executive summary ("16 completed · 6 reviews ready · 34 waiting"), an explicit "Next action / what's holding this up?" strip, a high-level 5–8 phase map, and six collapsible audience lanes. Opening a lane shows its ordered tasks and dependencies.
- Overview cards display 3–8 word titles, *one* status word, optionally a short explanation. Never repeat a long slug twice on a card.
- Nodes display semantically named phases such as "Research competitors", "Check the research", "Prepare creatives", "Review and approve", "Stage ads", "Launch and verify". These are derived/explicit workflow metadata, not falsely inferred generic numbering.
- Primary detail drawer: **What this step does → What to do now → Required tools / Ads Gallery → Inputs / exact references → Outputs → Completion and QC → Who is responsible → What is blocked**. Group long prompts and policy JSON under collapsible "Full instructions / Technical details".
- Search includes human title, task ID, lane, phase and tags. Status filters include READY, RUNNING, NEEDS_REWORK, WAIT_DEPENDENCY, WAIT_APPROVAL, REVIEW_WAIT, COMPLETE, BLOCKED, UNKNOWN.
- Status counts reflect actual tasks: a review-kind node with \`status=READY\` is "Review ready"; \`NEEDS_REWORK\` is "Needs changes"; \`WAIT_DEPENDENCY\` is "Waiting for previous work". A dashboard MUST NOT show "Review 0" if review-kind tasks are READY merely because only REVIEW_WAIT was counted.
- Distinguish "workflow blocked" / "needs rework" from per-task \`BLOCKED\`. A summary of zero \`BLOCKED\` nodes must not conceal a real workflow-level gating condition.
- Always show last verified/advisory event sequence, current pinned revision, source timestamp, generated timestamp and "snapshot, not automatically live".
- Keyboard-accessible cards, headings, focus, responsive mobile layouts and accessible color/text badges; SVG arrows should be readable with horizontal scrolling and optional overview/minimap. No missing source field may be fabricated.

Detailed presentation spec and examples: [VISUALIZATION-AND-HANDOFF.md](VISUALIZATION-AND-HANDOFF.md).


## P0 accessibility design contract: contrast is a requirement, never a theme guess

**Incident:** The external chat-generated **"Six parallel audience lanes"** Bucket 9 workflow HTML used lane title text that was effectively white on a white or similarly pale card. This was unreadable even though the surrounding cards were otherwise usable. It is a design-system and test failure, not merely a single color preference.

**Normative design rules for all AOS-W-generated HTML, screenshots, interactive diagrams, and worked examples:**

1. **Explicit paired colors.** Every heading and meaningful label MUST declare or resolve BOTH its foreground and the actual surface background. Do not rely on color inheritance from a host, ChatGPT client, browser dark-mode defaults, parent card, SVG, theme plugin or CSS framework. In particular "Six parallel audience lanes" and every audience heading must have explicit tested pairs across all supported themes.
2. **WCAG 2.2 AA contrast:** normal text and labels at least **4.5:1**; qualified large text at least **3:1**; graph edges, focus outlines and meaningful non-text UI indicators at least **3:1**. As a release simplification, our automated audit targets **4.5:1 even for large sampled headings**. Standards: https://www.w3.org/TR/WCAG22/#contrast-minimum and https://www.w3.org/TR/WCAG22/#non-text-contrast.
3. **Theme coverage:** test light and dark color schemes, desktop width (~1440px) and mobile (~390px), hover/focus/selected/waiting/completed and high-contrast/forced-colors where supported. A white text token cannot appear on a white audience tile because a parent theme flipped its surface. The label must stay legible independently of the operating system theme.
4. **No opacity-as-legibility control.** Never fade *readable text* to 30% opacity for search nonmatches or inactive-but-visible steps; use alternate high-contrast surfaces/borders while retaining text contrast.
5. **Not color alone:** all task statuses must be written as words; arrows/edges should remain visible at 3:1, and keyboard focus must have a visible text-independent outline. Titles must use adequate size (prefer 13–16px+ for labels) and line wrapping. No critical content may be clipped at 200% browser zoom, within reasonable workflow canvas scrolling.
6. **Verification is mandatory before declaring an HTML visualization deliverable.** The agent should proactively run the optional local Chromium contrast audit \`python scripts/aosw-contrast-audit.py --html <index.html> --out <audit-folder>\`, inspect screenshots and fix low contrast autonomously. If no headless browser exists, use any available host/browser alternative and programmatic WCAG contrast calculation; record precise limitation rather than refusing to generate a usable diagram or asking for an unnecessary human gate. This is a code/design quality check, **not an added human approval gate**.
7. **Fail-closed release CI:** a small synthetic six-lane example MUST fail if changed to white-on-white and MUST pass light/dark/desktop/mobile computed-style checks. Tests of real generated graphs must also cover main lane headings, step titles, status chips, links, phase headings, banners, sidebar headings and SVG dependency arrows. Archive screenshots and measured minimum ratios. Unverified screenshots cannot be represented as audited.
8. **Independent-visualization portability:** A chat-made custom HTML view is subject to these rules even if it does not use the canonical AOS-W viewer. When possible, require a shared contrast helper/test rather than bespoke unreviewed colors.

The paired tokens are specified in the installed \`references/visualization-viewer.html\` and the public-safe [six-lane example](../../../examples/visualization/six-lane-accessible.html). A previous chat artifact cannot be retroactively repaired by editing this spec; regenerated examples and future outputs must comply.

## P0-04. HTML-first presentation; GitHub Pages by default WHEN safe

If hosting on GitHub and the user asks to **open a workflow webpage**, the first offered link MUST be a functioning **rendered HTTPS page**, not \`github.com/.../blob/.../index.html\` showing raw source.

Decision sequence:
A. Agent host supports authenticated HTML preview: render there and provide real view link. Keep \`index.html\` in agent-files.
B. User/organization has a verified **private GitHub Pages** capability and authenticated access control, AND explicitly authorized publication: publish to that private Pages site and test readback/access. GitHub's private Pages access controls currently require qualifying GitHub Enterprise Cloud organizational setup; a private source repository by itself is not a private website.
C. Content is intentionally public-safe, separately sanitized, and owner explicitly authorized public publication: publish a **separate approved export** to GitHub Pages and link the rendered URL.
D. Otherwise: provide a direct standalone HTML file/link via an authenticated workspace/file host and explain that public Pages is unsafe for private instructions. Never treat a raw GitHub blob as a satisfactory interactive preview or automatically publish private run data. An archive is an explicit last resort.

For Pages deployment, use a dedicated sanitized export source/branch/site and explicit deployment allowlist; NEVER deploy \`agent-files/\` directly. Validate content disclosure (prompts, customer data, logos/licensing, secrets, private URLs), authorization, target visibility, repo/site configuration, deployment status, response content, graph revision and freshness. Provide an actual URL obtained from the host/provider, not one constructed by assumption. Verify that the browser opened it, that the served content matches the intended snapshot, and no private data are exposed. Where restricted access cannot be verified, stop deployment.

A v0.9 viewer can have a stable authorized \`/latest/\` route plus immutable event-scoped snapshots. Static Pages is a **published snapshot**, not live workflow monitoring. Automatic refresh requires a separate tested host watcher/trigger and explicit publication scope; a stale "current" alias must state its last event/time. Updating another agent's live run must not rewrite checkpoints or make publication a blocking dependency.

External guidance: GitHub Docs' Pages creation and visibility documentation warns that a private repository does not establish private site access. Public and private visibility depend on account type and site settings:
https://docs.github.com/en/enterprise-cloud@latest/pages/getting-started-with-github-pages/changing-the-visibility-of-your-github-pages-site

## P0-05. Predictable agent discovery via AGENTS.md

Adopt the open \`AGENTS.md\` convention as a **small, nonauthoritative entry point**, not a second workflow instruction hierarchy:
- Optional repo root entry or installed \`aos-w/AGENTS.md\` for hosts that discover scoped instructions.
- Explain AOS-W layout and a "new human/agent: start here" sequence, authoritative \`PROTOCOL.md\`, \`VERSION.json\`, instance pointer, event/checkpoint verification, permissions and safety.
- Existing unrelated AGENTS.md MUST be preserved; add scoped block or nested AGENTS.md only with explicit compatible install policy. No blind overwrite.
- AGENTS.md can link current handoff, but never hardcode "latest g0004" as permanent truth. Read on-disk instance/run records.
- Support both an unfamiliar human README and a predictable agent AGENTS.md; neither contains credentials.
Reference: https://agents.md/

## Essential v0.9 operational policy: Capability recovery, not capability excuses

**Owner directive, October 22, 2026:** Agents working on AOS-W workflows are expected to be capable and resourceful. A capability declaration is for task routing, discovery, diagnostics, and truthfulness—not a new prerequisite that lets an agent stop, complain, or demand a human to do work for it. **No capability-checker may create a new human approval gate.** Existing *explicit* security, publishing, spending, independent-review, and provider-permission gates stay in force.

A responsible execution agent MUST make a best-effort attempt to obtain and use the capabilities reasonably available in its environment, without asking the user to do routine work:
1. **Discover:** inspect the current host's tools, connected apps, approved local scripts/skills, workspace, browser and sources. Do not equate an unlisted capability with an absent capability.
2. **Acquire/route:** use another available suitable tool or already available independent reviewer; follow the instructions of trusted skills; delegate bounded tasks when an authorized mechanism exists. An internal tool name is not itself a requirement.
3. **Adapt:** if a particular source or UI fails, use permitted alternatives, recorded cached/historical evidence with correct caveats, or a human-readable equivalent method. Preserve required provenance and never invent observations.
4. **Advance independently:** complete all unaffected tasks and prepare dependent drafts without marking them approved. Failure to finish one step must not unnecessarily stop the whole workflow.
5. **Escalate narrowly:** only after a concrete attempted action, reproducible failure and no compliant alternative, record a specific blocker stating attempted tools, error, remaining needed capability and the next possible safe action. Ask for access/owner input **only if truly necessary**, not by default.
6. **Never fake:** independent QC, actual pixel inspection, live provider write/readback, or valid human authorization. If unavailable despite serious attempts, the exact required gated transition waits, but useful safe parallel work continues.

The agent's actual attempts, observations and recovery actions—not merely a claim like "I cannot browse"—determine when an execution blocker is justified. Human approval may be requested only where the existing owner policy already requires it or a genuine permission decision is needed; the capability profile itself cannot add one. All instructions to agents and evaluators must enforce this same norm.

## P0-06. Agent Skills conformance and capability-to-task matching

Retain existing trusted \`SKILL.md\` files and validate against the open Agent Skills format (frontmatter name/description, correctly scoped assets/references/scripts).
- A skill is an instruction/resource package, **not a permission grant or evidence of tool access**.
- Each step declares required capabilities and independently verified evidence of availability: \`browser_read\`, \`private_source_access\`, \`image_pixels\`, \`model_independent_review\`, \`git_write\`, \`meta_read\`, \`meta_stage\`, etc.
- A capability manifest lists \`id\`, \`description\`, provider/tool locator or host mapping, \`read|write\` scope, trust, verification tier/time, source evidence and denied operations; user-approved scopes and provider identity are separately checked.
- Agents MUST first try the available browser, authorized source links, skills, alternate permitted tools and reviewable historic evidence. A single failed Ads Gallery attempt or missing predeclared capability is **not** grounds to refuse, defer the whole workflow, or create an owner gate. If every compliant access path genuinely fails after documented attempts, record the precise research source gap, continue safe independent work, and never fabricate a live ad observation.
- Provide a nonmutating conformance linter and human-readable report first; do not rewrite users' existing skills without approval.
Reference: https://agentskills.io/specification

## P0-07. Structured, cold-start handoffs

AOS-W handoff records SHALL include human summary plus machine-ready references:
- Who is taking over; exact task ID, title and plain-language purpose; workspace & pinned graph; last saved verified/advisory event sequence.
- Full effective step brief and source catalog; tool access prerequisites; precise read/write boundaries; expected input/output and complete acceptance requirements.
- Artifact references with content hashes, latest reviewer verdict & independence basis; approvals required or absent; pending provider readback and any external unknown side effects.
- Resume instruction grounded in files, **not original conversation**.
- Audit provenance \`Agent | Platform | Role | Instance\`, previous session references and explicit unknown/unavailable data.
- A separately readable human \`handoff.md\` and machine \`handoff.json\` remain compatible; optional A2A mapping does not become an authority source.

A fresh human/agent should be able to perform a read-only dry-run of the step, identify required Ads Gallery or other services, correctly hold all Meta staging/launch gates and articulate a correct handoff without access to original ChatGPT messages.

## Optional P1 interoperability, not v0.9 shipping blockers

1. **MCP** adapter profile: map typed tools/resources/prompts to declared capabilities with explicit verified host availability and least-privilege scopes; never make MCP mandatory.
2. **A2A** profile: optional Agent Card discovery, task IDs/status mapping, signed/scoped artifact/reviewer exchanges and resume links; no implied background runner or independent-model proof simply from using a remote endpoint.
3. **Agent Plugin packaging**: optional manifest/export for approved skills and MCP dependencies; no credentials in exported bundle.
4. **OASF/catalog metadata**: standardized tags and human description to support a static curated GitHub registry; no paid marketplace required.
5. **OpenTelemetry mapping**: redacted trace/event export, source-of-truth remains validated local events, never external spans.
6. **Model/runtime adapter**: durable per-step operation IDs, retries/readback, LangGraph/Temporal-style checkpoint and human-interrupt semantics only when the host proves those guarantees.

References: https://a2a-protocol.org/v0.3.0/specification/ ; https://github.com/modelcontextprotocol/modelcontextprotocol ; https://docs.temporal.io/encyclopedia/event-history ; https://langchain-ai.github.io/langgraph/concepts/durable_execution/

## Data migration and authority

Introduce optional additive display fields under a separately versioned **v0.9 human presentation profile**, plus an optional Step Brief file/metadata projection. Do not rewrite old 0.7 template pins, 0.8 visualization schema snapshots, g0004 graph IDs, task dependency edges or event history. Existing 0.8.2 HTML must still open. A provider-specific rendered URL lives only in non-authoritative view metadata/publication record and must not be counted as task completion.

Where the JSON Schema currently sets \`additionalProperties:false\`, use a deliberately versioned compatible schema/profile or an approved \`extensions\` field; do not inject fields that invalidate existing canonical files. Generated human display titles must be clearly distinguished from approved stored ones. Migration of mandatory instructions requires a new pinned approved revision, not silent edits.

## Governance and release

- Product spec draft may be committed without owner approval. **Implementation and release of 0.9.0 require the owner's acceptance of this scope**, consistent with current unapproved stable V1 PRD.
- Never require live Meta, spend changes or GitHub Pages deployment to pass the *portable* offline tests. Use mocked/sanitized published-site tests; real deployment acceptance requires explicitly approved destination and visibility.
- No automatic public publishing based solely on private repository URL.
- The existing four unresolved stable V1 tests are not waived by v0.9 UX/interoperability work; independent QC and hosted locking remain distinct requirements.
- Consult [ACCEPTANCE-MATRIX.md](ACCEPTANCE-MATRIX.md) before calling any functionality complete. Status should be NOT STARTED until tests genuinely pass.

## Evidence and limits

This proposal draws on: the supplied Bucket 9 screenshot and current repo readback, AGENTS.md and Agent Skills specifications, A2A v0.3.0, MCP specs, LangGraph and Temporal durability, and GitHub Pages docs.
